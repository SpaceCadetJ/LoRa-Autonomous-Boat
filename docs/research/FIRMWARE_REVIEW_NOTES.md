## 1. Link-loss failsafe

**Verdict: CONFIRMED — there is no link-loss failsafe of any kind. The last commanded thrust and rudder persist indefinitely if the handset goes silent.**

### Evidence

The only use of `HAL_GetTick()` in the whole firmware is the telemetry send timer. The main loop in full (`main.c:454-486`):

```c
  while (1)
  {
    /* Handle GPS parsing */
    gps_task();                                   // main.c:457

    /* Process any complete LoRa line */
    if (lora_ready)                               // main.c:460
    {
      lora_ready = 0;
      char buf_local[LORA_BUF_LEN];
      strncpy(buf_local, lora_buf, sizeof(buf_local));
      buf_local[LORA_BUF_LEN - 1] = '\0';
      dbg("LORA RX: "); dbg(buf_local); dbg("\r\n");
      parse_lora_line(buf_local);                 // main.c:471
    }

    uint32_t now = HAL_GetTick();                 // main.c:474

    /* Send *our* GPS over LoRa every 5 seconds if valid */
    if (gps_valid && (now - last_lora_tx >= 5000U))   // main.c:477
    {
      ... lora_send_payload(payload);             // main.c:481
      last_lora_tx = now;                         // main.c:482
    }

    HAL_Delay(10);                                // main.c:485
  }
```

- `now` (`main.c:474`) is compared only against `last_lora_tx` (`main.c:112`, `main.c:477`), which is a *transmit* timestamp. There is no `last_lora_rx`, no "last command" timestamp, and no comparison that could detect silence from the handset. `grep HAL_GetTick main.c` yields exactly one hit (`main.c:474`).
- Thrust and rudder are applied immediately and only when a command arrives: `set_thrust()` at `main.c:335`, `set_rudder()` at `main.c:350`, both called from `parse_lora_line()`. Nothing else ever writes the compare registers after boot (`main.c:378`, `main.c:394`).
- There is no heartbeat/keep-alive message type; the parser recognises only `THRUST`, `RUDDER` and `GPS` (`main.c:327`, `main.c:342`, `main.c:357`).

### What persists if the handset goes silent

| State | Where held | Behaviour on link loss |
|---|---|---|
| `thrust_value` (0..100) | `main.c:115`, written `main.c:334/379` | Unchanged forever |
| `rudder_value` (0..100) | `main.c:116`, written `main.c:349/395` | Unchanged forever |
| TIM3 CCR1 (motor pulse, µs) | `main.c:378` | Timer hardware free-runs; the ESC keeps receiving the last pulse width at 50 Hz |
| TIM1 CCR1 (rudder pulse, µs) | `main.c:394` | Same; servo holds last position |

Because the PWM is generated by timer hardware, the outputs also persist if the CPU stops (hard fault, `Error_Handler`, see §8) — a hung MCU is indistinguishable from a healthy one at the ESC connector. Combined with §5 (no watchdog) and §7 (an overrun error permanently kills LoRa reception), a boat at full thrust can keep going with no path back to idle other than a power cycle.

## 2. PWM pin mapping, timer math, pulse mapping

**Verdict: PARTIAL — the firmware mapping (PA8/TIM1 = rudder, PC6/TIM3 = motor), the 50 Hz / 1 µs-per-count math and the 16 MHz timer-clock assumption are all CONFIRMED from the code and .ioc; but `docs/NETLIST.md` routes PA8 to the ESC and PC6 to the servo, the opposite of the firmware, and this contradiction is unresolved.**

### Pin/timer assignment (firmware)

| Function | Timer | Pin | `.ioc` | `hal_msp.c` | `main.c` helper |
|---|---|---|---|---|---|
| Rudder servo | TIM1_CH1 | PA8 | `.ioc:65-66` (`PA8.Signal=S_TIM1_CH1`), `.ioc:135` | `hal_msp.c:124-132` (AF1) | `set_rudder()` `main.c:387-396`, header `main.c:8` |
| Motor ESC | TIM3_CH1 | PC6 | `.ioc:78-79` (`PC6.Signal=S_TIM3_CH1`), `.ioc:137` | `hal_msp.c:145-153` (AF2) | `set_thrust()` `main.c:371-380`, header `main.c:9` |

The `main.c` header explicitly claims this is "actual, based on testing" (`main.c:7`).

**Contradiction with the PCB documentation:** `docs/NETLIST.md:159-162` puts net `PWM_MOTOR` on **U3-41 (PA8)** → `SPEEDCONTROLLER-2`, and `NETLIST.md:164-167` puts `PWM_RUDDER` on **U3-37 (PC6)** → `STEERINGSERVO-2`; the netlist author already flagged the swap at `NETLIST.md:169`. If the netlist is what is on the board, then at boot the ESC receives the *rudder* waveform (1500 µs centre = mid-throttle on a forward-only ESC) and the servo receives the *thrust* waveform (1000 µs = hard against one end-stop). This must be settled by measurement on the physical board before any V2 pin table is frozen.

### Timer clock and prescaler/period math

- Clock tree (`main.c:493-526`): HSI on (`main.c:503-505`), `PLL.PLLState = RCC_PLL_NONE` (`main.c:506`), `SYSCLKSource = RCC_SYSCLKSOURCE_HSI` (`main.c:517`), AHB/APB1/APB2 dividers all `DIV1` (`main.c:518-520`). The `.ioc` agrees: `RCC.CortexFreq_Value=16000000` (`.ioc:114`) and there are no `RCC.SYSCLKSource`/APB-divider overrides, so CubeMX defaults (HSI, /1) apply. The `PLLCLKFreq_Value=96000000` etc. at `.ioc:117-134` are CubeMX's computed defaults for an *unused* PLL and are not on any clock path.
- On the F4, `TIMxCLK = PCLKx` when the APB prescaler is 1 (it is 2×PCLK only when the prescaler > 1). With both APB dividers at /1: **TIM1CLK (APB2) = TIM3CLK (APB1) = 16 MHz.** The 16 MHz assumption is correct.
- Both timers: `Prescaler = 15`, `Period = 19999` (`main.c:540,542` for TIM1; `main.c:592,594` for TIM3; `.ioc:142-143`, `.ioc:148-149`).
  - Counter clock = 16 MHz / (15+1) = **1 MHz → 1 count = 1 µs**.
  - PWM period = (19999+1) counts = 20 000 µs = **50 Hz**.
  - Consequently the CCR value *is* the pulse width in microseconds, which is why `__HAL_TIM_SET_COMPARE()` is passed raw µs values (`main.c:378`, `main.c:394`).
- Auto-reload preload is enabled (`main.c:545`, `main.c:596`) and `HAL_TIM_PWM_ConfigChannel` enables CCR preload, so a new pulse width takes effect at the next update event (≤ 20 ms), glitch-free.

### Pulse mapping

Motor (`main.c:70-72`, `main.c:375-376`): `pulse = 1000 + (1000 * value) / 100` → exactly 10 µs per percent.

| thrust | pulse (µs) |
|---|---|
| 0 | 1000 (idle / `PWM_MOTOR_IDLE_US`, `main.c:72`) |
| 50 | 1500 |
| 100 | 2000 |

Rudder (`main.c:75-77`, `main.c:391-392`): `pulse = 1100 + (800 * value) / 100` → exactly 8 µs per percent.

| rudder | pulse (µs) |
|---|---|
| 0 (left) | 1100 (`PWM_RUDDER_LEFT_US`, `main.c:76`) |
| 50 (centre) | 1500 (`PWM_RUDDER_CENTER_US`, `main.c:75`) |
| 100 (right) | 1900 (`PWM_RUDDER_RIGHT_US`, `main.c:77`) |

Inputs are clamped to 0..100 twice (in the parser `main.c:332-333`/`347-348` and in the setters `main.c:373`/`389`). The thrust mapping assumes a forward-only ESC (1000 µs = stop); there is no reverse/neutral-at-1500 mode.

### .ioc vs main.c drift (regeneration hazard)

- `.ioc:150` sets the TIM3 initial pulse to **1500**, but `main.c:608` uses `PWM_MOTOR_IDLE_US` (**1000**). `MX_TIM3_Init()` is generated code outside any `USER CODE` block, so a CubeMX regeneration would restore 1500 µs (= 50 % throttle) as the power-on compare value.
- `main()` itself (`main.c:405-487`) contains **no** `USER CODE BEGIN 2 / WHILE / 3` markers. With `ProjectManager.KeepUserCode=true` (`.ioc:95`) only marked blocks survive regeneration, so regenerating from this `.ioc` deletes the NVIC setup, PWM start, LoRa init and the entire main loop.

## 3. LoRa configuration

**Verdict: CONFIRMED — the AT sequence, `AT+PARAMETER=12,7,1,4` (SF12 / BW index 7 = 125 kHz / CR 4-5 / preamble 4), `AT+SEND=2,<len>,<payload>` to address 2, and a 5 s telemetry period are all as read from the code. The `// SF12,BW7.8` comment is wrong (index 7 is 125 kHz). Module replies are never read, there is no application-level checksum, and the sender address is not checked.**

### AT command sequence (`main.c:445-449`)

```c
  lora_send_line("ATE0");                        // Echo off              main.c:445
  lora_send_line("AT+ADDRESS=1");                // This node (boat)      main.c:446
  lora_send_line("AT+NETWORKID=18");             // Network ID            main.c:447
  lora_send_line("AT+BAND=915000000");           // 915 MHz               main.c:448
  lora_send_line("AT+PARAMETER=" LORA_PARAM_STR);// SF12,BW7.8,CR4/5,PL=4 main.c:449
```

- `lora_send_line()` (`main.c:173-181`) transmits the string and then `\r\n`, each with a 100 ms blocking timeout. Commands are sent back-to-back with no wait for `+OK`/`+ERR`, and the module's replies are received by the ISR but discarded by the parser because they do not start with `+RCV=` (`main.c:298-301`). A rejected command is therefore invisible.
- The RYLR is never reset by the MCU: `NETLIST.md:87-90` routes `LORA_RST` to PA3, but PA3 is not in the `.ioc` pin list (`.ioc:20-32`) and never appears in `main.c`. The firmware cannot recover a wedged module and does not wait for the module's `+READY` banner; it relies solely on the fixed `HAL_Delay(1500)` at `main.c:438`.
- The literals `1`, `18`, `915000000` at `main.c:446-448` are hard-coded even though `LORA_ADDR_BOAT`, `LORA_NET_ID`, `LORA_FREQ` exist at `main.c:63-66`; only `LORA_PARAM_STR` (`main.c:67`) is actually used.

### `LORA_PARAM_STR "12,7,1,4"` (`main.c:67`)

RYLR `AT+PARAMETER=<SF>,<BW>,<CR>,<Preamble>`:

| Field | Value | Meaning |
|---|---|---|
| SF | 12 | Spreading factor 12 (slowest, longest range) |
| BW | 7 | **125 kHz** in both the RYLR896 table (0 = 7.8 kHz … 7 = 125, 8 = 250, 9 = 500) and the RYLR998 table (7 = 125, 8 = 250, 9 = 500) |
| CR | 1 | Coding rate 4/5 |
| Preamble | 4 | 4 symbols. On the RYLR998 a preamble other than 12 is only accepted when `NETWORKID=18`, which is consistent with `main.c:447` |

**Comment discrepancy:** `main.c:449` says `BW7.8`; 7.8 kHz would be BW index **0** on the RYLR896 and does not exist at all on the RYLR998. The value actually programmed is 125 kHz. Header comment `main.c:26` repeats the numeric string correctly.

**Module-variant risk:** `docs/BOM.csv:29` lists only the 5-pin header (`LORAMODULE`), not the module part. If the fitted module is an RYLR998, its command manual caps SF at 11 (and pairs allowed SF with BW); `AT+PARAMETER=12,7,1,4` would be answered with `+ERR` and, because replies are ignored, the module would silently keep its stored parameters. The RYLR896 generation accepts SF 7–12. Confirm the part number before relying on SF12.

**Airtime consequence (estimate, SF12 / 125 kHz / CR4-5 / preamble 4 / explicit header / CRC / LDRO on; T_sym = 32.8 ms):** a `THRUST,50` frame (≈9 B + module addressing) is ≈1.0 s on air; a `GPS,42.123456,-83.123456` frame (24 B) is ≈1.5 s. The command channel is therefore limited to roughly one packet per second per direction, and the boat's own 1.5 s telemetry burst every 5 s (`main.c:477`) blocks reception (half-duplex) for ~30 % of the time.

### AT+SEND payload format and destination

`lora_send_payload()` (`main.c:188-198`):

```c
  snprintf(cmd, sizeof(cmd), "AT+SEND=%d,%u,%s",
           LORA_ADDR_RC,              /* 2 */                       main.c:194
           (unsigned)strlen(payload), payload);                    main.c:195-196
```

- Destination = `LORA_ADDR_RC` = **2** (`main.c:63`). `cmd` is 128 bytes (`main.c:191`).
- Payload built at `main.c:479-480`: `"GPS,%.6f,%.6f"` into a 64-byte buffer, e.g. `AT+SEND=2,24,GPS,42.123456,-83.123456`.
- **Telemetry period: 5000 ms** (`main.c:477`), gated on `gps_valid` (see §4 for why this gate is sticky).
- `%f`/`%.6f` formatting (`main.c:364`, `main.c:480`) and `sscanf("%f")` (`main.c:360`) require newlib float support (`-u _printf_float` / `-u _scanf_float`) with newlib-nano. No `.cproject`/Makefile is committed under `firmware/` (only the `.ioc` and two `.ld` files), so this cannot be verified from the repo; if float support is off, the GPS payload is emitted without numbers and the RC-GPS echo never parses.

### `+RCV=` parsing (`main.c:282-368`)

- ISR side (`main.c:709-727`): one byte at a time into `lora_buf[LORA_BUF_LEN=128]` (`main.c:60`, `main.c:102`). A `\n` terminates the line and sets `lora_ready` (`main.c:713-718`). Bytes beyond 127 are **silently dropped** (`main.c:721-724`); the truncated line is still delivered and parsed. No length field, no CRC, no framing error check.
- Main side copies the buffer (`main.c:463-465`), echoes it on the debug/GPS UART (`main.c:467-469`), then `parse_lora_line()`:
  1. skips leading CR/LF/space/tab (`main.c:287-290`), returns on empty (`main.c:292`);
  2. requires prefix `+RCV=` or `RCV=` (`main.c:298-301`), otherwise returns silently — this is how `+OK`, `+ERR=n`, `+READY` are discarded;
  3. skips to the second comma (`main.c:304-311`) — i.e. past `<src addr>,<len>,` — and returns if fewer than two commas (`main.c:311`). The `<len>` field is not used to delimit the payload and the `<src addr>` is **never checked**, so any node on network 18 at the same RF parameters can drive the boat;
  4. strips trailing CR/LF (`main.c:315-319`);
  5. matches `THRUST,` / `RUDDER,` / `GPS,` with `strncmp` (`main.c:327/342/357`) and extracts values with `sscanf` (`main.c:330`, `345`, `360`); trailing `,<RSSI>,<SNR>` is ignored because `sscanf` stops after the first `%d`.
- **Malformed input:** every failure path is a silent `return` or a failed `sscanf` with no action and no counter. A partially corrupted byte inside the digits (e.g. from a UART framing error, §7/§9) that still yields a parseable integer *is* applied to the motor — there is no checksum, sequence number or plausibility filter on the value.
- **No checksum at the application layer.** The LoRa PHY CRC (handled inside the RYLR) protects the air link only; the 115200-baud UART between module and MCU is unprotected.
- **Single-buffer race:** `lora_ready` is set by the ISR while the main loop may be inside a blocking `dbg()` call (`main.c:467-469`, each up to 100 ms at 9600 baud) or `HAL_Delay(10)` (`main.c:485`). A second line arriving in that window overwrites `lora_buf` from index 0 (`main.c:717`, `main.c:723`) before `strncpy` at `main.c:464` runs. With ~1 s LoRa airtime this is unlikely for `+RCV` lines but does happen with the five `+OK` replies during init (harmless there because they are ignored).

## 4. GPS parsing

**Verdict: PARTIAL — RMC-only parsing with an A/V validity check and a real XOR checksum is CONFIRMED; but `gps_valid` is never cleared after a fix is lost (stale position keeps being transmitted), and the single RX buffer is overwritten by the next NMEA sentence before the main loop copies it, so RMC lines are likely to be dropped most of the time.**

### What is parsed

- Sentences: only `$GPRMC` / `$GNRMC` (`main.c:275`, re-checked at `main.c:243-247`). GGA/GSA/GSV/VTG/GLL are discarded — so no altitude, HDOP, satellite count or speed/course is available.
- Validity: field 2 must be `'A'` (`main.c:250`); on `'V'` the code sets `gps_valid = 0` and returns (`main.c:252-253`).
- Checksum: **present** — `gps_validate_checksum()` (`main.c:214-227`) XORs every byte between `$` and the last `*` (`main.c:217`, `main.c:221-224`), parses the two hex digits with `strtol` (`main.c:225`) and rejects on mismatch. The trailing `\r` left in the buffer (only `\n` is stripped, `main.c:694`) is harmless because `strtol` stops at it.
- Lat/lon conversion `gps_ddmm_to_deg()` (`main.c:201-211`): `atof` of `ddmm.mmmm`, `deg = (int)(v/100)`, `minutes = v - deg*100`, `deg + minutes/60`, negated for `S`/`W` (`main.c:204-208`). Arithmetically correct. Result is truncated to `float` (`main.c:209`, stored at `main.c:107-108`) — ~4–8 × 10⁻⁶ ° resolution (≈0.5 m), so the `%.6f` printed later (`main.c:480`) carries one digit of false precision.
- What is done with the fix: **telemetry only**. `gps_lat`/`gps_lon`/`gps_valid` are read in exactly one place, the 5 s `AT+SEND` at `main.c:477-483`. There is no navigation, waypoint, heading or return-to-home logic anywhere in the firmware despite the project name.
- Buffers: `GPS_BUF_LEN = 128` (`main.c:59`); ISR buffer `gps_buf` (`main.c:96`) with overflow guard at `main.c:702-705` (excess bytes dropped, line still delivered); `gps_task()` copies to a 128-byte stack buffer (`main.c:271-273`); `gps_parse_rmc()` tokenises in place into at most 16 pointers (`main.c:234-240`). An RMC sentence is ≈70–80 bytes, so 128 is adequate.

### Defect A — `gps_valid` is sticky after fix loss (`main.c:237-241`, `main.c:250-254`)

Tokenising uses `strtok` (`main.c:237`), which **collapses consecutive commas**. A void RMC as emitted by most receivers has empty fields, e.g. `$GNRMC,120000.00,V,,,,,,,160926,,,N*7D`, which yields only 5 tokens. `gps_parse_rmc()` then returns at `main.c:241` (`if (n < 7) return;`) *before* reaching the `'V'` test at `main.c:250` and never clears `gps_valid`. Result: once a fix has been obtained, losing it leaves `gps_valid = 1` with the last coordinates, and the boat keeps transmitting that stale position every 5 s indefinitely (`main.c:477-483`). Only sentences that still carry populated lat/lon with status `V` reach the clearing path.

The same `strtok` behaviour means any empty field *before* the lat/lon fields (e.g. missing time on a cold receiver) shifts the field indices; `toks[2]` is then not the status field.

### Defect B — ISR/main race on `gps_buf` (`main.c:694-706`, `main.c:271-273`, `main.c:485`)

When `\n` arrives the ISR terminates the string, sets `gps_ready`, and resets `gps_len = 0` (`main.c:696-698`). The very next byte — the `$` of the following sentence — is written to `gps_buf[0]` (`main.c:704`). The main loop copies `gps_buf` only when `gps_task()` runs (`main.c:457`, `main.c:272`), which is at best one loop iteration later: `HAL_Delay(10)` (`main.c:485`) plus any blocking `dbg()` output (`main.c:467-469`, `338-339`, `353-354`). At 9600 baud one byte takes ≈1.04 ms, so with typical 10–50 ms latency the first 10–50 bytes of the RMC line have already been replaced by the next sentence (`$GPVTG…` on u-blox and MediaTek default orderings, which emit VTG immediately after RMC). The copied buffer then fails `strncmp(buf, "$GPRMC")` at `main.c:275` (or fails the checksum) and the fix is dropped. Parsing only succeeds when the receiver leaves an inter-sentence gap longer than the loop latency, or when RMC happens to be the last sentence of the epoch. This needs a bench check (count of parsed RMC per minute); the fix is a second "ready" buffer filled in the ISR, or a ring buffer.

## 5. Peripherals NOT initialised

**Verdict: CONFIRMED — ADC, CAN, IWDG, WWDG, RTC and USB are absent from the .ioc IP list, from `main.c`, from `hal_msp.c`/`it.c`, and are disabled in `hal_conf.h`. The PA2 battery divider has no reader. Additionally the LoRa reset line (PA3) is undriven and the on-board CAN transceiver is unused.**

### Evidence

- `.ioc:10-17` — the complete IP list is `NVIC, RCC, SYS, TIM1, TIM3, UART4, USART3` (`Mcu.IPNb=7`). No `ADC*`, `CAN*`, `IWDG`, `WWDG`, `RTC`, `USB_OTG_FS`.
- `.ioc:20-32` — the complete pin list is PA0, PA1, PB0, PC6, PA8, PA13, PA14, PA15, PC10, PC11, PB3, SysTick. **PA2 is not configured** at all (left as reset-state analog/floating input).
- `main.c:121-126` — only `SystemClock_Config`, `MX_GPIO_Init`, `MX_UART4_Init`, `MX_USART3_UART_Init`, `MX_TIM1_Init`, `MX_TIM3_Init` exist; `main.c:416-420` calls exactly those. No `ADC_HandleTypeDef`, `CAN_HandleTypeDef`, `IWDG_HandleTypeDef`, `RTC_HandleTypeDef` or `PCD_HandleTypeDef` anywhere in `main.c`, `hal_msp.c` or `it.c` (grep `ADC|IWDG|WWDG|CAN|RTC|USB|PCD` over `firmware/Core/Src` returns nothing).
- `hal_conf.h:41` (`HAL_ADC_MODULE_ENABLED`), `:42` (`CAN`), `:58` (`IWDG`), `:61` (`RTC`), `:72` (`WWDG`), `:73` (`PCD`/USB) are all commented out, so the HAL drivers are not even compiled.
- `hal_msp.c` contains MSP init only for TIM1/TIM3 (`hal_msp.c:88-113`) and UART4/USART3 (`hal_msp.c:200-255`). `it.c` has only the Cortex handlers plus `UART4_IRQHandler` (`it.c:196-205`) and `USART3_IRQHandler` (`it.c:217-220`).

### Hardware that consequently goes unused (from `docs/NETLIST.md`)

| Net | MCU pin | Netlist | Firmware |
|---|---|---|---|
| `ADC_VBAT` (R5/R6 divider, TP2) | PA2 (U3-16) | `NETLIST.md:63-66` | Not configured; battery voltage is never read, no low-battery action possible |
| `LORA_RST` | PA3 (U3-17) | `NETLIST.md:87-90` | Not configured; MCU cannot reset the RYLR |
| TCAN1042H `CAN_TX`/`CAN_RX`/`CAN_STB` | PA11 / PA10 / PA12 | `NETLIST.md:125-138` | No CAN driver. Note also that the F446's CAN1 pins are PA11 = RX and PA12 = TX; PA10 has no CAN function, so the netlist's PA11-TX / PA10-RX / PA12-STB assignment could not be used by CAN1 without a hardware change (verify against the schematic) |
| `VBAT` | U3-1 | `NETLIST.md:205-208` | No RTC, and no LSE crystal pins in `.ioc:20-32`, so the backup domain is unused |

**No watchdog** is the safety-relevant omission here: with IWDG disabled (`hal_conf.h:58`, absent from `.ioc:10-17`), the infinite loops in `Error_Handler` (`main.c:736-742`) and the fault handlers (`it.c:82-137`) are permanent, with PWM frozen at the last value (§1, §8).

## 6. PB0

**Verdict: CONFIRMED — PB0 is configured as a push-pull output, written low once at init, and never changes state; on the PCB it is the `GPS_RX` net to GPS header pin 3, so the firmware is holding that GPS pin at 0 V permanently.**

### Evidence

- Header comment: `PB0 -> Debug LED / probe` (`main.c:10`).
- `.ioc:67-68`: `PB0.Signal=GPIO_Output`.
- `MX_GPIO_Init()` (`main.c:665-683`): `HAL_GPIO_WritePin(GPIOB, GPIO_PIN_0, GPIO_PIN_RESET)` at `main.c:675`, then configured `GPIO_MODE_OUTPUT_PP`, no pull, low speed at `main.c:678-682`.
- Those are the **only** references to `GPIO_PIN_0` on port B in the reviewed sources (`hal_msp.c:216` uses `GPIO_PIN_0|GPIO_PIN_1` but on GPIOA for UART4). There is no `HAL_GPIO_TogglePin`, no second `WritePin`, and no use in any ISR. The pin is a constant logic 0 from a few ms after reset.
- `docs/NETLIST.md:106-109`: net `GPS_RX` — "MCU PB0 → GPS module (data to GPS)", pins `U3-26 (PB0), GPSMODULE-3`. The netlist author's own note says the firmware uses USART3 on PC10/PC11 instead (`NETLIST.md:107`), which matches `main.c:13` and `hal_msp.c:239-248`.

### Consequence

The GPS header therefore has two MCU-driven lines: pin 3 (PB0, constant low) and pin 5 (PC10 / USART3_TX, `NETLIST.md:116-119`, carrying the `dbg()` text at 9600 baud). What that does depends on which GPS-module signal lands on header pin 3:

- If pin 3 is the module's serial **RX** input (as the net name implies), it sees a permanent break condition — harmless for NMEA output, but any configuration commands must go via PC10 (which is currently spammed with debug text, `main.c:467-469`).
- If the module actually presents an **output** on pin 3 (TX or 1PPS on some breakout pinouts), a push-pull low on PB0 is a driver-to-driver contention.

Safest V2 stance until the header pinout is verified: configure PB0 as input (or analog) at init, or drive it high (idle UART level) if it really is the GPS RX line.

## 7. UART robustness

**Verdict: PARTIAL — interrupt-driven 1-byte reception on both UARTs is CONFIRMED; there is no `HAL_UART_ErrorCallback`, so an overrun error permanently disables reception on that UART (CONFIRMED from the HAL source); the widely-cited "blocking transmit timeout kills RX interrupts" behaviour is REFUTED for the HAL version in this repo.**

### Reception path

- Both UARTs are armed with single-byte `HAL_UART_Receive_IT` (`main.c:162-170`), first from `main.c:441-442`, then re-armed from inside `HAL_UART_RxCpltCallback` (`main.c:707`, `main.c:726`). Return values are ignored in all four call sites (`main.c:164`, `169`, `707`, `726`); a `HAL_BUSY`/`HAL_ERROR` would silently end the receive chain.
- Re-arming from the callback is legal with this HAL: `UART_Receive_IT` sets `RxState = READY` (`hal_uart.c:3673`) *before* invoking the callback, and `HAL_UART_Receive_IT` takes no lock (`hal_uart.c:1347-1366`).
- IRQ plumbing: `UART4_IRQHandler` → `HAL_UART_IRQHandler(&huart4)` (`it.c:196-205`), `USART3_IRQHandler` → `HAL_UART_IRQHandler(&huart3)` (`it.c:217-220`, in a user block because `.ioc:38-49` lists only `UART4_IRQn`). NVIC priority for UART4 is set to 0 in `hal_msp.c:224-225`, then overridden to 5 in `main.c:423-424`; USART3 is enabled only in `main.c:426-427` at priority 5. Equal priorities mean neither UART ISR can pre-empt the other. SysTick is priority 0 (`hal_conf.h:151`, `.ioc:47`).

### Overrun (ORE) handling — the real hole

`HAL_UART_IRQHandler` in the repo's HAL:

- With no error flags, RXNE simply calls `UART_Receive_IT` (`hal_uart.c:2364-2372`).
- With any error flag it still delivers the byte if RXNE is set (`hal_uart.c:2408-2411`) — so a byte with a **framing/noise error is passed to the application as data** (`hal_uart.c:2464-2476`, "Non Blocking error"). There is no per-byte error flag visible to `HAL_UART_RxCpltCallback`, so corrupted bytes enter `lora_buf`/`gps_buf` and, for LoRa, can be parsed into a thrust value (§3).
- On **ORE** the error is "blocking": `UART_EndRxTransfer()` is called (`hal_uart.c:2416-2421`), which clears `RXNEIE`/`PEIE`/`EIE` and sets `RxState = READY` (`hal_uart.c:3370-3385`), then the weak `HAL_UART_ErrorCallback` is invoked (`hal_uart.c:2445-2461`).
- **`main.c` does not define `HAL_UART_ErrorCallback`** (grep over `firmware/Core/Src` finds only `HAL_UART_RxCpltCallback` at `main.c:688`). The weak default does nothing, nobody re-arms `HAL_UART_Receive_IT`, and that UART is deaf until reset. On UART4 this means the boat stops accepting commands while the motor keeps the last thrust (§1). ORE requires the RX ISR to be delayed by more than one byte time (≈87 µs at 115200, ≈1 ms at 9600) — rare in this simple system, but it is a single, unrecoverable event (e.g. a debugger halt, a long critical section added later, or noise bursts at the module's boot).

### Blocking transmit timeouts

- `dbg()` → `HAL_UART_Transmit(&huart3, …, 100)` (`main.c:158`); `lora_send_line()` → two transmits with 100 ms each (`main.c:178`, `180`).
- At 9600 baud, 100 ms covers ≈96 characters. `dbg(buf_local)` at `main.c:468` can be handed up to 127 characters, so long LoRa lines are truncated mid-string with `HAL_TIMEOUT` returned and ignored. At 115200 the 100 ms budget is ample.
- **Refuted gotcha:** in older F4 HAL releases `UART_WaitOnFlagUntilTimeout` disabled `RXNEIE` on timeout, which would have killed IT reception on the same UART. In the HAL shipped here it simply returns `HAL_TIMEOUT` (`hal_uart.c:3212-3225`) and `HAL_UART_Transmit` restores `gState = READY` (`hal_uart.c:1174`, `1193`), so a debug-print timeout does *not* break GPS reception and TX recovers on the next call.
- `dbg()` shares the GPS UART: everything written for "debug" (`main.c:339`, `354`, `365`, `451`, `467-469`) is transmitted into the GPS module's RX line (`NETLIST.md:116-119`). There is no separate console; the strings are only observable by probing PC10.

### Other observations

- Blocking `HAL_UART_Transmit` calls run with interrupts enabled, so the RX ISRs continue during them; no `__disable_irq()` exists outside `Error_Handler` (`main.c:738`).
- The `lora_ready`/`gps_ready` flags and buffers are shared between ISR and main with no double-buffering (see §3 and §4 Defect B).
- No IDLE-line detection, no DMA, no ring buffer — every byte costs a full `HAL_UART_IRQHandler` pass (~100+ cycles at 16 MHz).

## 8. `Error_Handler` behaviour and startup ordering

**Verdict: CONFIRMED — `Error_Handler` disables interrupts and spins forever; all Cortex fault handlers spin forever with no watchdog to recover; PWM is started and set to idle/centre ~1.5 s before the LoRa module is configured, so the ESC sees a steady 1000 µs from a few ms after reset.**

### `Error_Handler` (`main.c:736-742`)

```c
void Error_Handler(void)
{
  __disable_irq();     // main.c:738
  while (1) { }        // main.c:739-741
}
```

- Interrupts disabled, no indication, no reset. It is reachable only from init paths: `main.c:430`, `431` (PWM start), `509`, `524` (RCC), `548`, `554`, `565`, `576` (TIM1), `599`, `605`, `613` (TIM3), `635` (UART4), `656` (USART3). If it fires at `main.c:430/431` the timer never starts and PC6/PA8 are static — the ESC will refuse to arm, which is the benign case. If it fires earlier, SysTick is dead too.
- Cortex fault handlers (`it.c:67-77` NMI, `82-92` HardFault, `97-107` MemManage, `112-122` BusFault, `127-137` UsageFault) are all bare `while(1)` loops, interrupts still enabled, PWM timers still running at the last CCR. A runtime fault (e.g. stack overflow — stack is 0x800 bytes, `.ld:42`, `.ioc:106`, while `main()`+`gps_task()`+`parse_lora_line()`+`lora_send_payload()` place 128+64+128+80+128 bytes of buffers on it and newlib's `%f` formatting adds ≈1 KB) therefore leaves the boat running at the last thrust with no recovery. No IWDG (§5).
- `assert_failed` (`main.c:745-749`) is a no-op and `USE_FULL_ASSERT` is off (`.ioc:93`).

### Startup ordering (`main.c:405-451`)

| Step | Line | ESC / servo see |
|---|---|---|
| `HAL_Init`, `SystemClock_Config` | `main.c:410-413` | Pins in reset state (high-Z inputs) |
| `MX_GPIO_Init` (PB0 low) | `main.c:416` | — |
| `MX_UART4_Init`, `MX_USART3_UART_Init` | `main.c:417-418` | — |
| `MX_TIM1_Init`, `MX_TIM3_Init` (pins switched to AF in `HAL_TIM_MspPostInit`, `hal_msp.c:115-160`; initial CCR 1500 µs / 1000 µs at `main.c:557`, `608`) | `main.c:419-420` | Static level, no pulses (timers not yet running) |
| NVIC priorities/enables | `main.c:423-427` | — |
| `HAL_TIM_PWM_Start` TIM1, then TIM3 | `main.c:430-431` | **Pulses begin:** 1500 µs on PA8, 1000 µs on PC6 (per firmware mapping) |
| `set_thrust(0)`, `set_rudder(50)` | `main.c:434-435` | Same values re-written (1000 µs / 1500 µs) — no glitch |
| `HAL_Delay(1500)` | `main.c:438` | Steady idle/centre for 1.5 s → a typical forward-only ESC arms here |
| `StartGPSRxIT`, `StartLoRaRxIT` | `main.c:441-442` | — |
| LoRa AT configuration | `main.c:445-449` | — |
| `dbg("Boat: LoRa init done")` | `main.c:451` | — |

So PWM starts **before** LoRa init, and the ESC sees a continuous 1000 µs from roughly 10 ms after reset. That is the correct order for safety (never start the radio before the outputs are in a known state), but note two things: (a) the ESC is armed automatically with no user gate, so the first `THRUST,n` received drives the motor immediately; (b) if the netlist swap in §2 is real, the ESC instead sees **1500 µs** at boot, which most ESCs treat as "not at minimum, refuse to arm" — or, on an auto-calibrating ESC, as mid throttle.

## 9. Clock / oscillator and UART baud accuracy

**Verdict: CONFIRMED — HSI only (no HSE, no LSE, no PLL); the divider error is ≤ 0.08 % at both baud rates, so the HSI tolerance dominates: ±1 % at 25 °C sits comfortably inside the ~3.3 % receiver budget, but the datasheet's over-temperature band (up to ±4 % or worse) does not.**

### Evidence

- `main.c:503-506`: `OscillatorType = HSI`, `HSIState = ON`, `HSICalibrationValue = DEFAULT`, `PLL.PLLState = RCC_PLL_NONE`. `main.c:517`: `SYSCLKSource = RCC_SYSCLKSOURCE_HSI`. AHB/APB1/APB2 = /1 (`main.c:518-520`), flash latency 0 (`main.c:522`), regulator scale 3 (`main.c:500`) — all consistent with 16 MHz.
- `.ioc:114` `RCC.CortexFreq_Value=16000000`. No `PH0/PH1` (HSE) or `PC14/PC15` (LSE) pins in `.ioc:20-32`. The PLL/VCO values at `.ioc:117-134` are unused defaults.
- All UART and timer clocks are therefore derived from the untrimmed HSI (`RCC_HSICALIBRATION_DEFAULT`, `main.c:505`); there is no run-time trimming against an external reference.

### Baud-rate divider error (16 MHz, oversampling 16, `main.c:632`, `653`)

| UART | Baud (`main.c`) | Ideal USARTDIV | Programmed BRR | Actual baud | Divider error |
|---|---|---|---|---|---|
| UART4 (LoRa) | 115200 (`main.c:626`) | 8.6806 | 8 + 11/16 = 8.6875 | 115 108 | −0.080 % |
| USART3 (GPS) | 9600 (`main.c:647`) | 104.1667 | 104 + 3/16 = 104.1875 | 9 598 | −0.020 % |

### Error budget

The STM32 receiver tolerates ≈3.33 % total clock deviation for 8-bit frames with 16× oversampling and a non-zero BRR fraction (RM0390 "USART receiver tolerance to clock deviation" table; 3.75 % with a zero fraction). Typical peer receivers (RYLR MCU, GPS MCU) are quoted at 2–3 %.

| Condition | HSI error (STM32F4 datasheet, verify DS10693 table) | + divider | Share of 3.33 % budget | Share of a 2.5 % peer budget |
|---|---|---|---|---|
| 25 °C, factory trim | ±1 % | 1.08 % | 32 % | 43 % |
| −10 … 85 °C | −4 / +4 % | up to 4.1 % | **>100 %** | **>100 %** |
| −40 … 105 °C | −8 / +4.5 % | up to 8.1 % | >100 % | >100 % |

Peer-side crystal error (typically ±50–100 ppm) is negligible by comparison. A sealed electronics box on the water in summer can exceed 60 °C, where the HSI is typically 2–3 % off: enough to produce intermittent framing errors that, per §7, are delivered as data with no checksum (§3). Consequences beyond UART: SysTick and therefore the 5 s telemetry period and all `HAL_Delay`s are ±1–4 %; the 1 µs PWM tick is likewise ±1–4 % (±15–60 µs at 1500 µs) — insignificant for the servo, but it shifts the ESC's throttle end-points slightly.

Remedies for V2: fit the HSE crystal (footprint decision on the PCB), or at minimum use the RYLR/GPS traffic to detect framing errors and add an application checksum.
